# OutcomeX 产品设计 v0.1

## 1. 产品定位

**OutcomeX** 是一个面向 AI Agent 和自动化软件的可验证链上数据服务网络。

用户不注册套餐、不购买 API Key，只需要在请求中用 USDC 按次付款。服务商提交结果和证明，验证通过后自动结算。OutcomeX 从每笔成功订单中收取 1% 协议费。

一句话定位：

> 让机器可以发现服务、验证结果，并用稳定币按次购买链上数据。

## 2. 第一批目标用户

### 买方

- 需要实时链上数据的 AI Agent
- 自动化交易和风控机器人
- 钱包、研究和分析工具开发者
- 不想维护多套 API 账户和信用卡账单的开发团队

### 卖方

- 链上数据服务商
- RPC 和索引服务提供者
- 交易策略或风险分析服务商
- 运行专用节点、解析器和验证器的个人开发者

## 3. v0.1 只做三种服务

第一版只支持确定性强、可以复核的服务，不做主观判断型服务。

默认部署选择：Base Sepolia 测试网 -> Base 主网，结算资产使用 USDC。合约使用 Solidity，后端和 SDK 使用 TypeScript，数据存储使用 PostgreSQL。第一版只接入一个 RPC/索引服务，等订单量证明需求后再增加冗余供应商。

1. `wallet_snapshot`
   - 输入：钱包地址、链、区块高度
   - 输出：原生币余额、ERC-20 余额、主要 NFT 持仓、最近转账
   - 证明：区块高度、查询参数、结果哈希、数据源签名

2. `contract_events`
   - 输入：合约地址、事件签名、区块范围
   - 输出：规范化事件列表
   - 证明：区块范围、日志索引、RPC 返回证明

3. `token_price_snapshot`
   - 输入：交易对、链、区块高度
   - 输出：指定区块附近的价格和流动性快照
   - 证明：池子地址、储备量、区块号、计算过程哈希

暂时不支持网页抓取、新闻判断、信用评分和投资建议，因为这些结果难以在第一版中客观仲裁。

## 4. 买方流程

1. Agent 查询服务目录。
2. Agent 选择服务和价格上限。
3. Gateway 返回 HTTP 402 和支付要求。
4. Agent 用 USDC 签名付款。
5. Gateway 将请求转给服务商。
6. 服务商返回结果、结果哈希和证明。
7. 验证器复核结果。
8. 结算合约按比例分账：服务商 98%，验证奖励池 1%，OutcomeX 协议金库 1%。
9. Agent 收到 JSON 结果和链上收据。

采用 x402 作为支付传输层，但 OutcomeX 的验证、托管和结算是额外服务，不把自己包装成 x402 本身。

## 5. 协议费用

每笔订单按成交额收取 1%，设置最低费用以覆盖结算成本。

示例：

- 服务商报价：0.10 USDC
- 买方支付：0.10 USDC
- 服务商收到：0.098 USDC
- 验证奖励池：0.001 USDC
- OutcomeX 金库：0.001 USDC

协议费直接进入公开的金库地址。v0.1 不发行代币，不承诺收益，也不把金库余额包装成投资产品。

## 6. 结果和证明格式

每个服务响应都包含：

```json
{
  "requestId": "0x...",
  "serviceId": "wallet_snapshot",
  "chainId": "base",
  "blockNumber": 12345678,
  "inputHash": "0x...",
  "result": {},
  "resultHash": "0x...",
  "provider": "0x...",
  "proof": {
    "source": "rpc-or-indexer-url",
    "attestation": "0x..."
  },
  "expiresAt": 1780000000
}
```

第一版只接受能被复核的证明。不要先做“人工判断市场”，否则会迅速变成客服和仲裁公司。

## 7. 合约边界

合约只做四件事：

- 锁定买方付款；
- 记录订单和结果哈希；
- 在验证成功后按比例结算；
- 在超时或确定性验证失败时退款。

建议的接口：

```solidity
createOrder(bytes32 serviceId, bytes32 requestHash, uint256 amount, uint64 expiry)
submitResult(bytes32 orderId, bytes32 resultHash, bytes calldata proof)
settle(bytes32 orderId, address provider)
refund(bytes32 orderId)
challenge(bytes32 orderId, bytes32 evidenceHash)
```

实际请求不必每次都单独上链，可以在 L2 上批量提交结果哈希，减少 Gas。支付和签名使用成熟的稳定币授权流程，不自行保存用户私钥。

## 8. 信任模型

v0.1 采用“确定性服务优先”的原则：

- 同一输入和同一区块应得到可重复结果；
- 验证器可以独立重放查询；
- 结果必须绑定区块高度和输入哈希；
- 服务商需要抵押少量 USDC；
- 发现伪造结果时，买方可以在短时间内发起挑战；
- 争议逻辑只覆盖明确的格式和数据一致性错误。

不要在第一版宣称“完全去中心化”。第一版可以由你运行 Gateway 和一个验证器，但订单、付款、结果哈希和协议费必须公开可查。

## 9. API 草案

```text
GET  /v1/services
POST /v1/quote
GET  /v1/services/{serviceId}/request
POST /v1/orders/{orderId}/challenge
GET  /v1/orders/{orderId}/receipt
```

SDK 目标：

```ts
const result = await outcomeX.request("wallet_snapshot", {
  chain: "base",
  address: wallet,
  block: "latest"
}, {
  maxPayment: "0.05 USDC"
});
```

## 10. 30 天开发计划

### 第 1 周：能付款

- 部署测试网结算合约；
- 实现服务目录；
- 接入 x402 风格的 402 支付流程；
- 完成一个 `wallet_snapshot` 服务；
- 返回支付收据和结果哈希。

### 第 2 周：能验证

- 加入 `contract_events`；
- 实现独立重放验证器；
- 加入超时退款；
- 编写 TypeScript SDK；
- 记录每个订单的请求、结果和结算状态。

### 第 3 周：能被别人使用

- 上线开发者文档；
- 提供一个公开演示 Agent；
- 接入 3 个外部服务提供者；
- 做一个简单的服务商控制台；
- 发布 10 个真实可调用的服务端点。

### 第 4 周：验证是否有人付费

- 找 20 个 AI Agent 或链上工具开发者；
- 让至少 5 个完成集成；
- 争取 3 个付费用户；
- 目标是 100 个真实付费请求，而不是注册量；
- 第一阶段月收入目标：100–500 USDC。

## 11. 成功与失败标准

### 继续投入的条件

- 至少 3 个陌生开发者愿意付费；
- 服务商能持续提供稳定结果；
- 付费请求中至少 30% 来自重复用户；
- 争议率低于 2%；
- 每笔订单的链上和基础设施成本明显低于协议费。

### 应该换方向的信号

- 用户只愿意免费试用，不愿意发起真实订单；
- 服务商不愿意抵押或提供可复核证明；
- 订单金额太小，Gas 和验证成本吞掉全部收入；
- 买方真正想要的是主观研究结论，而不是确定性数据。

## 12. 暂不做的事情

- 不发代币；
- 不做公链；
- 不做跨链桥；
- 不托管私钥；
- 不提供杠杆、收益或投资建议；
- 不在第一版支持任意网页数据；
- 不用金库余额向用户承诺分红。

## 13. 第一批销售话术

> 你的 Agent 每次调用链上数据都要注册 API、管理额度和处理账单。OutcomeX 让它直接用 USDC 按次调用可验证数据服务，并返回带区块高度和结果哈希的收据。你只为成功请求付款，不需要订阅。

## 14. 最重要的产品判断

OutcomeX 的护城河不是“用了区块链”，而是：

- 可验证结果格式；
- 失败退款和争议规则；
- 服务商声誉与历史履约数据；
- 让 Agent 可以自动发现、选择和支付服务的 SDK；
- 真实订单形成的服务质量数据。

如果 v0.1 证明了一个垂直场景有稳定交易量，再扩展到通用的可验证 API 市场。

## 15. 当前实现边界

当前代码已经实现本地服务目录、报价、内存订单、确定性 Mock Provider、可选只读 EVM RPC Provider 和模拟收据。RPC 读取会固定到一个区块高度，并记录区块哈希（如果节点返回），但这仍不是独立密码学证明。

当前页面的执行按钮不会发起钱包授权或链上转账。真实付款验证器、x402 签名解析、Base Sepolia 结算合约部署和链上收据接入属于下一阶段。
